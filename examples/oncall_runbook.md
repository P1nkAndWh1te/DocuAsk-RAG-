# DocuAsk OnCall Runbook

这份文档用于演示运维知识库 RAG。内容覆盖常见告警、排查步骤、证据来源和安全边界。

## API 5xx 错误率升高怎么排查？

当 `order-service` 或 `payment-service` 出现 `HighErrorRate` 告警时，优先确认最近 10 分钟是否有发布、配置变更或上游依赖异常。

排查步骤：

1. 查看服务的 `http_5xx_rate`、`request_total` 和 `latency_p95` 指标。
2. 在日志中搜索 `ERROR`、`timeout`、`connection refused`、`database unavailable`。
3. 检查上游网关和下游依赖，例如 Redis、MySQL、第三方支付接口。
4. 如果 5xx 从发布后开始升高，优先考虑回滚或切流。

安全边界：不能直接重启所有实例，应先保留现场证据，再按发布记录和错误日志判断。

## Redis 连接超时怎么排查？

当应用日志出现 `Redis timeout`、`connection timeout` 或 `pool exhausted` 时，通常需要同时检查客户端连接池和 Redis 服务端状态。

排查步骤：

1. 查看 Redis 的 `connected_clients`、`used_memory`、`blocked_clients` 和 `ops_per_sec`。
2. 检查应用连接池配置，例如最大连接数、等待时间、超时时间。
3. 查看是否存在慢查询、大 key、网络抖动或 Redis 主从切换。
4. 如果只有单个服务受影响，优先检查该服务的连接池和调用量。

安全边界：不要直接清空 Redis 数据；需要先确认 key 类型、业务影响和恢复方案。

## MySQL 慢查询告警怎么排查？

当出现 `SlowQueryHigh` 或接口延迟升高时，优先确认慢查询 SQL、执行计划和索引情况。

排查步骤：

1. 查看慢查询日志，确认 SQL、耗时、扫描行数和发生频率。
2. 使用 `EXPLAIN` 检查是否走索引、是否出现全表扫描、临时表或文件排序。
3. 对照最近发布记录，确认是否新增了未加索引的查询条件。
4. 如果慢查询影响核心接口，可以先限流、降级或回滚，再补索引。

安全边界：不要在高峰期直接执行大表 DDL；需要评估锁表风险和回滚方案。

## CPU 使用率持续升高怎么排查？

当服务触发 `HighCPUUsage` 告警时，需要区分是正常流量增长、死循环、GC 压力还是依赖异常导致的重试风暴。

排查步骤：

1. 查看 `cpu_usage`、`qps`、`error_rate`、`latency_p95` 是否同时升高。
2. 检查最近是否有发布、定时任务、批处理任务或流量突增。
3. 结合日志查看是否存在大量重试、异常堆栈或热点接口。
4. 如果 CPU 升高伴随错误率升高，应优先定位错误来源，而不是只扩容。

安全边界：扩容可以缓解压力，但不能替代根因排查。

## 磁盘空间不足怎么处理？

当机器或容器出现 `DiskAlmostFull` 告警时，优先确认增长最快的目录和文件类型。

排查步骤：

1. 查看磁盘使用率、inode 使用率和最近增长最快的目录。
2. 检查日志目录、临时文件、上传文件和备份文件。
3. 如果日志异常增长，先确认是否有错误循环或 debug 日志误开。
4. 清理前确认文件是否仍被进程占用，必要时重启对应服务释放句柄。

安全边界：不要直接删除数据库数据目录、业务上传目录或未知目录。

## 告警处理通用原则

OnCall 处理告警时，目标不是立刻执行危险操作，而是先收集证据、判断影响范围、选择低风险动作。

通用流程：

1. 判断告警级别、影响服务和影响用户范围。
2. 收集指标、日志、发布记录和依赖状态。
3. 根据 runbook 和历史故障案例给出可能原因排序。
4. 优先执行低风险缓解动作，例如切流、限流、回滚、扩容。
5. 如果证据不足，应该升级给人工值班同学，而不是让系统编造原因。

安全边界：Agent 可以给出排查建议和证据引用，但不能自动执行高风险操作。
